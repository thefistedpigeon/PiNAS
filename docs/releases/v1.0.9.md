# PiNAS v1.0.9 — Disk maintenance and HTTPS convenience fixes (development candidate)

This is an **unreleased maintenance candidate** following v1.0.8. It is not an official release until reviewed and published.

## Disk wipe and format fix
In v1.0.8, the destructive helper called `wipefs` separately for each partition and disk, then independently called `blockdev --rereadpt`. On disks whose kernel partitions were still held briefly by udev, the redundant reread could report `BLKRRPART: Device or resource busy` after signatures had already been removed. This prevented the Format Disk operation from creating a new filesystem and left Mount Disk with nothing eligible to mount.

The helper now submits all eligible partition/disk paths in **one** `wipefs --lock=yes --all --force` invocation, with partitions listed before the whole drive, and **does not** call `blockdev --rereadpt` afterward. The util-linux `wipefs` tool already notifies the kernel about changed partition tables. The lock reduces races with `systemd-udevd`.

All existing disk eligibility checks, admin-password approval, explicit Yes checkbox, root-owned helper separation, and separate Mount Disk workflow remain intact. A genuine busy kernel device still causes a safe failure; this fix does not force removal of mounted or active devices.

## HTTP to HTTPS convenience redirect
PiNAS remains an HTTPS-only application for authenticated traffic. Plain HTTP requests made to the **same port** (normally 8765) now receive an HTTP **307 Temporary Redirect** to HTTPS at the Raspberry Pi's local interface IP and that port. HTTPS requests continue to be served directly using the same self-signed certificate.

The redirect runs in the existing threaded HTTP server. It does not start a separate process or port and does not trust user-controlled `Host` headers for the redirect destination. Invalid or failed TLS handshakes do not receive application data. Browser certificate warnings for a self-signed certificate are expected and are **not** bypassed.

## Storage adoption and Manage Disk usability fixes
- After a successful wipe, **Manage Disk stays open** and instructs the user to format the drive. After formatting, it refreshes the available filesystems inline and opens the **Adopt without formatting** section. Only a successful mount/adoption closes the card automatically.
- The privileged adoption helper tolerates missing optional boot mounts, checks filesystem type and UUID directly with `blkid -p` after a recent format, and verifies the actual mounted filesystem with `findmnt --mountpoint`.
- Failures now include the failing storage command and return code, rather than the unhelpful `Storage command failed` message.
- The browser-based updater now refreshes the root-owned `pinas-nas-storage` adoption helper and sudoers rule, ensuring existing installations receive the fixes.

## Validation
- Source and standalone installer generated from the same modules.
- Tests for the single locked `wipefs` invocation and no redundant `blockdev` call.
- Loopback HTTP request test confirming same-port HTTPS redirect and Host-header isolation.
- Existing PyNAS tests, Python compilation and embedded JavaScript syntax.

## On-device verification
1. Upgrade using the development-branch installer on a test Raspberry Pi with a spare USB disk containing **no valuable data**.
2. Verify a plain `http://<Pi-IP>:8765` request redirects to `https://<Pi-IP>:8765/`. The self-signed certificate still needs browser acknowledgement.
3. Use Wipe Disk, then Format Disk on the disposable drive. Confirm no redundant `BLKRRPART` error occurs.
4. Verify that Manage Disk remains open after wiping or formatting, the formatted filesystem appears immediately with a UUID and the **Adopt without formatting** button mounts it. Verify the dialog closes only after a successful mount.
5. Confirm mounted, boot/system, RAID and fstab-configured disks continue to be refused.

**Limitations:** This regression fix was verified by automated tests, not an actual USB drive attached to a Raspberry Pi. If `wipefs` itself returns a kernel busy error, the helper will continue to abort rather than bypass protections.
