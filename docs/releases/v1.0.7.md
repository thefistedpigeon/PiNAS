# PiNAS v1.0.7 — Update history and scheduled-update service health

**Unreleased development candidate.** PiNAS v1.0.6 remains the latest official release; do not merge until Raspberry Pi tests pass.

## Update history
- New **Installed update history** card on System Updates, recording manual and scheduled OS APT upgrade attempts, start/completion times, success/failure, up to 120 package names and a short APT summary.
- New separate SQLite file: `/var/lib/pinas-update-history/updates.sqlite3`. The directory and database are root-owned, accessible to PiNAS only for reading, and are independent of the regular PiNAS `config.json`.
- A retention selector allows **6 months** (default) or **12 months**. Saving it prunes older rows immediately; future installations prune automatically. A second cap holds a maximum of 2,000 events. Each event's summary and package list are bounded, with SQLite incremental space reclamation.
- Historical upgrades completed **before this build** cannot be reconstructed reliably and will not appear in the new database.
- The database records OS upgrades, not general journal messages, individual APT index checks or PiNAS application-package uploads.

## Scheduled-update service health
- Updates now includes a status card for `pinas-auto-updates.timer` and `pinas-auto-updates.service`.
- Overview → NAS service health shows both units and warns when a scheduled timer is stopped or a previous automatic update job failed.
- The automatic-update service is a **systemd one-shot service**. Its inactive state after a successful run is normal and not treated as a failure. If scheduling is off, both units are clearly reported as disabled/inactive instead of generating false alerts.
- Failed units display a **Restart** action requiring the current administrator password and session CSRF. Restarting the service triggers an immediate APT upgrade; restarting the timer restores the saved schedule. Neither restarts the PiNAS web dashboard itself.
- No extra long-running monitoring daemon was introduced. Service checks are on demand from Overview or Updates.

## Upgrade compatibility
Browser-based PiNAS upgrades now refresh the installed, narrowly scoped `pinas-apt-index` privileged helper and sudo rules when extracting the new release. This is needed for scheduled updates to use the new logging behaviour immediately after upgrading from v1.0.6. Existing schedules and NAS data are preserved.

## Hardware testing
1. Upgrade a disposable PiNAS v1.0.6 instance through Settings → Update PiNAS; confirm it reconnects and the installed `pinas-apt-index` helper is updated.
2. On System Updates, set the history retention to 6 then 12 months; verify values persist and the database permissions prevent standard NAS share users from opening it.
3. Install a harmless, available OS package upgrade; check the manual update outcome and package list appear.
4. Configure an automatic update schedule and run `sudo systemctl start pinas-auto-updates.service` in a test environment; verify the scheduled log entry appears and the completed inactive one-shot service displays as healthy.
5. Simulate a failed auto-update job only on a disposable test Pi. Verify the warning appears on Overview and Updates; test password-protected Restart. Do not intentionally interrupt APT on a production NAS.
6. Confirm intentionally disabled scheduling displays as disabled without error warnings, and that Restart is unavailable when no failure exists.
7. Reboot and confirm the SQLite history persists, the timer respects the configured schedule and there is no new persistent polling process.
8. Verify the Python 3 standard-library-only solution remains responsive on a Raspberry Pi 3B.

## Caveats
Update history remains bounded, but an interrupted SQLite write or full system disk can prevent a log entry from being recorded. APT failures are still reported independently by the existing updater. Changing retention from 12 to 6 months permanently removes older rows. Keep NAS backups independently of update history.
