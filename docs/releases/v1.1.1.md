# PiNAS v1.1.1 — Samba and Linux Permissions Consistency (candidate)

This security/consistency release implements the POSIX ACL and Samba share-policy principles discussed in [Deepak Nagarkoti's Samba on RHEL guide](https://nagarkotideepak9.medium.com/mastering-samba-on-rhel-a-complete-beginner-to-advanced-guide-to-linux-file-sharing-with-windows-06a81108d3f6), adapted to Raspberry Pi OS Lite and Debian Samba. Unlike RHEL, PiNAS uses `apt`, the `smbd` service and normally does not use SELinux.

## Account and share model

- PiNAS NAS users have matching Linux `pinas-nas` group identities and enabled Samba `smbpasswd` accounts. The Linux shells remain `nologin`; PiNAS does not enable shell or SSH login for NAS users.
- Creating a share verifies its eligible disk mount and each existing Linux/Samba identity before creating content.
- Private shares have `guest ok = no`, explicit `valid users`, and `write list` for users allowed to write. The filesystem folder is root-owned with named POSIX ACL grants for precisely those users. Read-only users receive `r-x`, read/write users `rwx` on directories, and inheritance is configured using POSIX default ACLs and Samba `inherit acls = yes`.
- Creating a user's optional private home share uses exactly the same restricted share-and-ACL helper, with only that username authorised.
- Guest shares use the local `nobody` identity, not anonymous filesystem-wide `chmod 777`. Public read-only folders grant read/traverse via a named `nobody` ACL; public writable folders grant write via the same scoped identity. Samba still enforces the selected guest access policy. **Public shares remain intentionally discoverable by trusted LAN clients** and are less secure than authenticated private shares.

## Editing shares and repairing existing content

- Every administrator share edit now automatically synchronises Linux ACLs on existing files and folders in a background job. The former optional checkbox is removed.
- The policy reconciler removes historical named grants for managed NAS users and `nobody` before reapplying the saved access policy, so previously authorised users do not silently retain outdated ACLs.
- Group and other access are explicitly denied when synchronising a managed tree. New subfolders inherit the current policy; existing file permissions are updated without changing their names, ownership or contents.
- Symlinks are not followed and nested mounted filesystems cause refusal before any recursive ACL changes. Large directories may take time. If an edit succeeds but ACL synchronisation fails, PiNAS reports the partial result; choose **Repair access** to retry.
- POSIX *file ownership* is not rewritten. Consequently, the existing Linux owner of a file can have rights locally even if the user is no longer listed in an SMB share; the Samba share itself and its root ACL still block unauthorised network traversal. This is deliberate to avoid unexpected ownership changes to existing data.

## Security and compatibility

- PiNAS continues to prefer independent per-user ACLs over RHEL-style shared-group `chmod 770`: the NAS can grant one user read/write and another read-only without granting every NAS group member the same access.
- No global Samba `acl_xattr:ignore system acls = yes` configuration is enabled; the POSIX ACL layer remains authoritative for local filesystem operations.
- `testparm -s` validates generated Samba settings before reloading `smbd`.
- A restricted privileged share helper enforces mount and device safeguards and serialises share transactions.
- Existing share files are preserved; no destructive migration or automatic chown is performed.

## Suggested on-device regression checks

1. Create a NAS user with private home share and verify only that user can browse/write via Windows SMB and PiNAS Files.
2. Create a private shared folder with one RW and one RO user; ensure the RO account cannot modify/delete, while RW can.
3. Add another user to an existing share; confirm access to existing files after automatic reconciliation.
4. Remove an account from the share; confirm SMB denial and check POSIX ACL removal with `getfacl -p` on both existing and new files.
5. Test public read-only and guest writable shares; verify the share root's Linux 'other' permission bits are **not writable**. Windows 11 may block insecure guest logons; prefer authenticated shares.
6. Test with a larger library and confirm the UI reports ACL reconciliation progress/failure instead of silently leaving stale permissions.
7. Verify no chmod/chown changes to unrelated folders, other disks, system partitions or mounted nested filesystems.
