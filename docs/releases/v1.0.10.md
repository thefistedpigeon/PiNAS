# PiNAS v1.0.10 — Share paths and private home shares (development candidate)

**Unreleased.** This version adds a lowercase on-disk share directory, private home-share provisioning, and optional migration for legacy share folders.

## New share directory

New shares use `/mnt/pinas/<filesystem-UUID>/pinas-shares/<share-name>` rather than `PiNAS Shares`. This affects only shares created after the update. Existing Samba shares retain their recorded path until explicitly migrated; there is **no automatic data move or rename**.

The PiNAS web file browser and share editor now accept both directory conventions using the root-owned share metadata, while refusing paths outside the current mounted drive's supported share roots.

## Optional private home share

The **Create NAS user** dialog adds a **Create private home folder share** checkbox. When checked:

- Select a mounted and persistently configured NAS filesystem.
- Confirm the administrator password.
- PiNAS creates the NAS/Samba account and then a Samba share named after its username.
- The directory is `/mnt/pinas/<UUID>/pinas-shares/<username>`, with a root-owned directory, restrictive mode, and POSIX ACLs granting the named NAS user read/write access and denying other NAS users.
- Samba `valid users` and `write list` are restricted to the new account. Files created inside the folder inherit ACL permissions.
- If the share operation fails **after** user provisioning, the response clearly states the account has been created. It does **not** delete the account or any files; the administrator can create the share manually.

Private shares are optional. When not selected, NAS account creation remains unchanged.

## Migrating an existing share

On the Shares page, managed shares whose current path contains `PiNAS Shares` offer **Move folder**. This action requires the current administrator password and an explicit server-side confirmation.

The root-owned helper validates the existing path and persistent mounted filesystem, refuses destination collisions/symlinks/nested mountpoints, uses a same-filesystem directory rename (no file copying), updates the Samba share path and PiNAS share metadata, validates the new Samba configuration, and reloads Samba. A failed configuration update attempts to restore the original path and configuration. **Existing SMB clients should close files before migrating**, as a directory rename can interrupt active file access.

The migration is not automatic. Always back up important data before migrating and verify the SMB share and web file browser afterward.

## Validation

Automated checks cover the generated standalone installer, Python compilation, browser script syntax, restricted helpers, share path compatibility, private access policy, and opt-in migration safeguards. **Physical Raspberry Pi and Samba client testing is still necessary** before declaring the release complete.

### Recommended on-device tests

1. Verify an existing legacy share remains accessible after installing the test build.
2. Create a new ordinary share; verify it appears in `pinas-shares`, is writable by the authorised user, and visible in the PiNAS file browser.
3. Create `beneliott` with **Create private home folder share** checked. Confirm `pinas-shares/beneliott` and that only `beneliott` can access it by SMB and the web file browser.
4. Attempt access as another NAS user; the private share must be denied.
5. With files closed and backed up, migrate the original `Dan` share using **Move folder**, and verify no data is lost and the share remains available.
6. Restart Samba and reboot. Confirm both new and migrated shares work across restarts.
7. Confirm the migration action refuses an existing target directory and external or missing mounts.
